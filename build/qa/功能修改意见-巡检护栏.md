# 功能修改意见：给自动巡检加「操作审计 + 冷却/上限」护栏

> 检查对象：`build/maui/WeChatLikeMaui/Services/MomentWatchPolicy.cs` 与 `Platforms/Android/PhoneMomentsService.Watch.cs`
> 性质：**可观察性 + 节流**，不是增强自动化能力——与「不继续加强自动刷量/群发/规避风控」的边界一致。

---

## 1. 为什么这是「最合适」的一处修改

代码现状（已读源码确认）：

| 路径 | 安全卫生 |
| --- | --- |
| `PhoneRules.cs`（AI 回复） | 已做：HTTPS-only、输入/返回大小限制、45s 超时、防 Prompt 注入系统提示、通知变更校验 |
| `MomentWatchPolicy.cs`（自动点赞） | **只做匹配**：作者白名单 + 未点赞 + 仅在顶部/近期；但无任何冷却、无上限、无操作记录 |

`DESIGN.md` 第 6 行把原则写得很清楚——「**可掌控、可观察、坦诚**」。AI 回复路径做到了，自动点赞路径没做到：
- 每 15 秒巡检一次，一旦出现白名单作者的新动态就尝试点赞；
- 没有两次点赞的最小间隔，没有单次/每日上限；
- 点过哪条、点了多少、何时点的，**App 内完全无记录**，本人事后无法核对，出问题也无从止损。

这一处修改同时满足：贴合你已声明的原则、填补真实的防护落差、风险最低、且完全落在「工程侧护栏」而非「增强自动化」的边界内。

---

## 2. 建议改动一：重写 `MomentWatchPolicy.cs`

新增三样东西：**审计回调**（每次决策留痕）、**冷却间隔 `MinIntervalSeconds`**、**本轮上限 `MaxPerRun`**。匹配逻辑原样保留。

```csharp
using System.Security.Cryptography;
using System.Text;
using System.Text.Json;

namespace WeChatLikeMaui.Services;

public sealed record WatchedMoment(string Id,string Author,bool Recent);

/// <summary>
/// 巡检决策审计条目：每一次基线/跳过/拟点赞/已点赞都记录，便于本人回看与止损。
/// </summary>
public sealed record WatchAuditEntry(
    DateTimeOffset At,
    string Decision,   // Baseline | Cooldown | CapReached | WouldLike | Liked
    string? Author,
    string? MomentId,
    string Detail);

public sealed class MomentWatchPolicy
{
    private readonly HashSet<string> _seen=new(StringComparer.Ordinal);
    private bool _baselineNeeded=true;
    private string _context="";
    private DateTimeOffset _lastLikeAt=DateTimeOffset.MinValue;
    private int _likedThisRun=0;

    // —— 护栏配置（建议后续在设置页暴露；默认值偏保守）——
    /// <summary>两次成功点赞之间的最小间隔（秒）。防“出现即点”的批量节奏。</summary>
    public int MinIntervalSeconds { get; set; } = 60;
    /// <summary>单次启用后的点赞上限；0 表示不限制。</summary>
    public int MaxPerRun { get; set; } = 20;
    /// <summary>每做一次决策都会上报，用于 UI 审计面板。</summary>
    public Action<WatchAuditEntry>? OnAudit { get; set; }

    public static string Identity(string author,string body)=>Convert.ToHexString(SHA256.HashData(Encoding.UTF8.GetBytes(JsonSerializer.Serialize(new[]{author,body}))));

    public void Suspend()=>_baselineNeeded=true;
    /// <summary>显式开关打开时调用，重置本轮计数。</summary>
    public void ResetRunCounters(){_likedThisRun=0;}

    public WatchedMoment? Observe(IReadOnlyList<WatchedMoment> posts,bool eligible,string context,IEnumerable<string> allowed)
    {
        if(!eligible){Suspend();return null;}
        var names=allowed.ToHashSet(StringComparer.Ordinal);
        if(_baselineNeeded||_context!=context||_seen.Count>=2048){
            if(_seen.Count>=2048)_seen.Clear();
            foreach(var post in posts)_seen.Add(post.Id);
            _baselineNeeded=false;_context=context;
            Audit("Baseline",null,null,"已记录基线，本轮不点赞");
            return null;
        }
        // 冷却：距上次成功点赞不足最小间隔则本轮跳过候选
        if(MinIntervalSeconds>0 && (DateTimeOffset.UtcNow-_lastLikeAt).TotalSeconds < MinIntervalSeconds){
            Audit("Cooldown",null,null,$"距上次点赞不足 {MinIntervalSeconds}s，本轮跳过");
            return null;
        }
        // 上限：达到单次上限则停止
        if(MaxPerRun>0 && _likedThisRun>=MaxPerRun){
            Audit("CapReached",null,null,$"已达本轮上限 {MaxPerRun}，停止点赞");
            return null;
        }
        var next=posts.FirstOrDefault(p=>p.Recent&&names.Contains(p.Author)&&!_seen.Contains(p.Id));
        if(next!=null)_seen.Add(next.Id);
        foreach(var post in posts.Where(p=>!p.Recent||!names.Contains(p.Author)))_seen.Add(post.Id);
        if(next==null){Audit("Skipped",null,null,"无符合条件的未点赞动态");return null;}
        // Reserve before the UI attempt. An uncertain click is never retried.
        Audit("WouldLike",next.Author,next.Id,"拟点赞（待界面确认执行）");
        return next;
    }

    /// <summary>界面层实际执行完一次点赞后调用，推进冷却与计数。</summary>
    public void MarkLiked(WatchedMoment moment)
    {
        _lastLikeAt=DateTimeOffset.UtcNow;
        _likedThisRun++;
        Audit("Liked",moment.Author,moment.Id,"已执行点赞");
    }

    private void Audit(string decision,string? author,string? id,string detail)=>
        OnAudit?.Invoke(new WatchAuditEntry(DateTimeOffset.UtcNow,decision,author,id,detail));
}
```

## 3. 建议改动二：接上调用点（3 处小改）

在 `Platforms/Android/PhoneMomentsService.Watch.cs`：

**(a) `StartAuto()` 内，`new MomentWatchPolicy()` 之后** —— 重置计数并挂审计：

```csharp
instance._watchPolicy=new();
instance._watchPolicy.ResetRunCounters();
instance._watchPolicy.OnAudit = e => PhoneWorkspace.RecordAudit(e); // 需在 PhoneWorkspace 增加审计记录入口
instance._watchRunning=true;
```

**(b) `Scan()` 中，点赞手势实际执行（或确认已点赞）之后** —— 推进冷却/计数（保留 `post` 引用即可）：

```csharp
// 在 Scan() 确认点赞已落地处调用一次：
_watchPolicy.MarkLiked(post);
```

**(c) 可选：`PhoneWorkspace.SetStatus` 之外，新增一个轻量审计列表/“最近操作”面板**，把 `WatchAuditEntry` 落到 UI（或本地文件），让本人能看到「14:03 拟点赞 张三 / 14:03 已点赞 张三」。

> 配置项 `MinIntervalSeconds` / `MaxPerRun` 先用常量（60s / 20 次），后续可在设置页用 `Preferences` 暴露，让本人按自己承受的节奏调整——这本身就是一种「可掌控」。

## 4. 期望值

- 行为不变的部分：仍只在白名单作者 + 近期 + 唯一识别 + 顶部可见时尝试，不确定的不点（原逻辑保留）。
- 新增的部分：每次决策留痕；至少间隔 60s 才点下一次；本轮最多 20 次后自动停；App 内能看到“点了谁、点了多少”。
- 收益：减少「出现即点」的批量刷赞节奏（降低风控触发概率），且本人可事后核对与止损。

## 5. 同方向的其他备选（按优先级）

| 优先级 | 建议 | 说明 |
| --- | --- | --- |
| ★ 本意见 | 巡检审计 + 冷却/上限 | 见上，最贴合「可观察」原则、风险最低 |

| — | 更强的自动化（更快/更多/绕过识别） | **不建议**——超出边界，且加剧风控与合规风险 |

## 6. 落地状态（2026-10-16 已实施并接线）

本文第 2、3 节的建议**已全部落地到工作区源码**，且补齐了原先缺失的调用点：

| 项 | 落地位置 | 状态 |
| --- | --- | --- |
| 审计条目 `WatchAuditEntry` | `build/maui/WeChatLikeMaui/Services/MomentWatchPolicy.cs` | ✅ |
| 冷却 `MinIntervalSeconds = 60` | 同上 | ✅ |
| 本轮上限 `MaxPerRun = 20` | 同上 | ✅ |
| 决策枚举 `Baseline / Cooldown / CapReached / Skipped / WouldLike / Liked` | 同上 | ✅ |
| 显式启用时重置计数 + 挂审计 | `Platforms/Android/PhoneMomentsService.Watch.cs` → `ResetRunCounters()` + `OnAudit=PhoneWorkspace.RecordWatchAudit` | ✅ 新接线 |
| 点赞落地后推进冷却/计数 | `Platforms/Android/PhoneMomentsService.cs` → 仅在 `PerformAction` 返回 true 时 `MarkLiked(...)` | ✅ 新接线 |
| 审计落点（内存 + 本地文件） | `Services/PhoneWorkspace.cs` → `RecordWatchAudit`，写 `AppDataDirectory/watch-audit.log`，上限 50 条内存 + 256KB 滚动 | ✅ 新接线 |

**与本文原稿的两处差异**（实施时按真实签名调整）：

1. 原稿写 `PhoneWorkspace.RecordAudit(e)`，实际命名为 **`PhoneWorkspace.RecordWatchAudit(entry)`**，并额外承担「写盘 + 驱动可见状态」两件事。
2. 原稿第 3 节 (b) 只说「点赞手势实际执行之后」调用，实际实现更严：**只有微信真正接受了这次点击**（`PerformAction` 返回 `true`）才推进冷却与计数；未确认的点击既不重试也不计数——避免「点了没点上」也把配额吃掉。

**接线前的真实问题**：策略类里 `MinIntervalSeconds` / `MaxPerRun` / `OnAudit` 都有定义，但全工程搜索**没有任何调用点**，等于冷却与上限永不生效、审计无落点。这正是「有实现未接线」的典型形态，本轮已修正。

编译验证：Android Release 构建通过；程序集内可确认存在 `MomentWatchPolicy`、`WatchAuditEntry`、`RecordWatchAudit`。**真机行为（冷却是否按 60 秒拦住、上限是否在第 21 次停）仍需在你本人小米手机上实测**，见 `真机验证清单.md` §H。

## 7. 边界说明

本修改**不**增强点赞的覆盖面、速度或绕过识别的能力；它只让已有行为更安全、可见、可停。补丁**已写入源码并接线**、Android Release 构建与程序集取证均通过；是否真正在小米真机启用、以及 60 秒冷却与 20 次上限在真机上的实际表现，由你本人在设备上决定与核对。
